각 단계마다 **무엇을 왜 만들었는지, 어떤 결정을 내렸는지, 어떻게 확인했는지**를 남겨서
나중에 다시 봐도 흐름을 이해할 수 있게 하는 것이 목적이다.

## 1단계: 준비물

- **날짜**: 2026-09-25
- **상태**: 완료 (사용자 확인 대기)

### 목표

앱 코드를 만들기 전에, 앱이 읽을 **예시 퀴즈 데이터**와 **AI에게 퀴즈를 만들어 달라고 할 때 쓸 프롬프트 템플릿**을 먼저 준비한다.
데이터 형식을 먼저 확정해 두면, 이후 단계(파일 읽기, 검사기, 엔진)를 이 예시 파일로 바로 시험할 수 있다.

### 진행 과정

1. **CLAUDE.md 확인**: 퀴즈 형식(필드 규칙), 폴더 구조, 1단계 완료 기준을 확인했다.
2. **계획 설명 → 사용자 의견 반영**: 처음에는 예시 덱 2개(생화학, 세계지리)를 제안했으나,
   사용자가 실제 공부하는 과목 5개로 만들어 달라고 요청했다.
   → 생화학, 생약학, 유기화학, 분석화학, 물리약학 5개 덱을 만들기로 변경.
   또한 제작 과정을 기록할 문서(이 파일)를 추가로 요청받았다.
3. **덱 파일 5개 작성**: 과목별로 6~7문제씩, 객관식과 주관식을 섞어서 작성.
4. **`decks/index.json` 작성**: 5개 덱 파일의 경로를 등록.
5. **`docs/PROMPT.md` 작성**: 새 덱을 AI로 만들 때 복사해서 쓰는 프롬프트 템플릿.
6. **형식 검사**: 임시 검사 스크립트(프로젝트 밖 임시 폴더에 두고 사용)로 모든 덱이 규칙을 지키는지 확인.
7. **CLAUDE.md 갱신**: 진행 상황 체크, 폴더 구조와 작업 규칙에 이 문서(DEVLOG.md) 추가.

### 내린 결정과 이유

- **작업 폴더를 `quiz-app/` 자리로 사용**: CLAUDE.md의 폴더 구조는 `quiz-app/`으로 시작하지만,
  실제 작업 폴더는 `quiz_system_project/`이므로 이 폴더 안에 바로 파일을 만들었다.
- **과목명(`subject`)은 한국어, 폴더명·deckId는 영어**:
  - `subject`는 홈 화면에 그대로 보이는 이름이라 한국어로 했다. (생화학, 생약학, 유기화학, 분석화학, 물리약학)
  - 폴더명과 `deckId`는 파일 경로·기록 키로 쓰이므로 띄어쓰기·한글 문제가 없는 영어 소문자로 했다.
    (`biochem`, `pharmacognosy`, `orgchem`, `analchem`, `physpharm`)
- **deckId 규칙**: `<과목약어>-<두 자리 번호>`. 같은 과목의 다음 덱은 `biochem-02`처럼 번호만 올린다.
- **파일명 규칙**: `<두 자리 번호>-<주제 영문>.json`. 폴더 안에서 번호 순으로 정렬되게 했다.
- **주관식 복수 정답**: 한글 이름, 영문 이름, 약어를 함께 넣었다. 예: `["시스테인", "Cys", "C", "cysteine"]`
  - 앱이 채점할 때 띄어쓰기와 영문 대소문자를 무시할 예정이므로, 그것만 다른 표기는 넣지 않았다.
- **테스트용 다양성 확보**: 각 덱에 객관식·주관식·해설 있음·해설 없음·복수 정답이 모두 들어가게 해서
  이후 단계에서 여러 경우를 한 번에 시험할 수 있게 했다.
- **PROMPT.md에 "기존 문제의 id·deckId는 바꾸지 말 것" 안내 추가**: 설계 원칙 1(문제 ID 불변)을 사용자도 지킬 수 있도록.

### 확인 방법과 결과

CLAUDE.md의 "형식 검사" 항목을 그대로 옮긴 임시 파이썬 스크립트로 검사했다.

검사한 항목:
- JSON 문법 오류 없음
- 머리말 필수 필드(`deckId`, `subject`, `title`, `questions`) 존재
- `deckId`가 덱끼리 겹치지 않음
- 문제 `id`가 정수이고 덱 안에서 겹치지 않음
- `question`, `answer`가 비어 있지 않음
- 객관식: `choices` 2개 이상, `answer`가 `choices` 중 하나와 정확히 일치
- 주관식: `answer`가 빈 문자열/빈 배열이 아님
- 1단계 조건: 덱마다 5문제 이상, 객관식·주관식·해설·복수 정답이 모두 포함

결과:

```

pharmacognosy-01   생약학    문제 6개 (객관식 3, 주관식 3, 해설 4, 복수정답 3)
orgchem-01         유기화학   문제 6개 (객관식 3, 주관식 3, 해설 4, 복수정답 3)
analchem-01        분석화학   문제 6개 (객관식 3, 주관식 3, 해설 4, 복수정답 3)
physpharm-01       물리약학   문제 6개 (객관식 3, 주관식 3, 해설 4, 복수정답 3)
오류: 없음
```

## 2단계: 뼈대와 파일 읽기

- **날짜**: 2026-09-25
- **상태**: 완료 (사용자 확인 대기)

### 목표

앱이 실제로 브라우저에서 열리고, `decks/index.json`에 등록된 덱 파일들을 읽어 홈 화면에 과목별로 목록을 보여주게 한다.
덱을 클릭하면 아직 퀴즈를 풀지는 않고 "선택한 덱: 제목, N문제"만 표시한다.

### 진행 과정 중 방향 확인

사용자가 "실제 문제를 만들어줄 필요는 없고, 그저 구동하는 시스템을 만들어주면 된다"고 명확히 함.
→ 1단계에서 넣은 예시 문제 내용의 사실 정확성은 더 신경 쓰지 않고, 이후 단계는 시스템(코드) 동작에 집중하기로 함.

### 만든 파일

| 파일 | 역할 |
|---|---|
| `index.html` | `<div id="app">` 하나만 있는 빈 컨테이너. `css/style.css`를 연결하고 `js/main.js`를 ES 모듈로 불러온다. |
| `css/style.css` | 기본 레이아웃. 고정 픽셀 폭 대신 `max-width` + 상대 단위 사용(추후 모바일 대응 고려). |
| `js/loader.js` | `decks/index.json`을 읽고, 그 안의 덱 파일들을 `fetch`로 하나씩 가져온다. |
| `js/ui/home.js` | 과목별로 덱 목록을 그리고, 클릭 시 선택 결과를 표시한다. |
| `js/main.js` | 시작점. `loader`로 덱을 불러온 뒤 `home.js`로 화면을 그린다. |

### 내린 결정과 이유

- **`loader.js`는 형식을 검사하지 않는다**: 3단계(`validator.js`)의 책임이므로, 지금은 `fetch`/`JSON.parse`가
  실패하면(파일 없음, JSON 문법 오류 등) 해당 덱만 `{ ok: false, error }`로 표시하고 나머지는 계속 읽는다.
  이렇게 해야 앱이 절대 멈추지 않는다는 CLAUDE.md 원칙을 지키면서도, 3단계에서 검사 로직만 별도 파일로
  추가하면 되게 구조를 미리 맞춰 둔 것이다.
- **읽기 실패한 덱은 홈 화면 위쪽에 경고로 모아 표시**: 3단계에서 요구하는 "파일명 + 이유" 표시를 지금부터
  준비해 둔다. 다만 지금은 "문제 id + 이유"까지는 다루지 않는다(파일 자체를 못 읽는 경우만 해당).
- **`renderHome`은 loader의 결과 배열을 그대로 받는다**: `engine.js`가 덱 구조를 몰라야 한다는 설계 원칙 2와
  마찬가지로, UI 계층도 각자 필요한 최소 데이터만 받게 하려 했다. `home.js`는 `deck.subject`, `deck.title`,
  `deck.questions.length`만 사용한다.
- **클릭 시 결과 표시는 `#selection` 영역 하나만 사용**: 이번 단계 완료 기준이 "선택한 덱: 제목, N문제" 표시이므로
  화면 전환 없이 같은 화면 아래에 나타나게 최소로 구현했다. 실제 풀이 화면 전환은 4단계에서 `ui/quiz.js`가 맡는다.

### 확인 방법과 결과

1. **서버 없이 열면 안 됨(`file://`)**: ES 모듈 + `fetch` 사용이므로 CLAUDE.md 규칙대로 로컬 서버가 필요하다.
2. `python3 -m http.server`로 임시로 띄워서 다음을 `curl`로 확인:
   - `index.html`이 정상 응답하는지
   - `decks/index.json`이 5개 덱 경로를 담고 있는지
   - `js/main.js`가 200 응답인지 (모듈 경로가 올바른지)
   - 모두 정상 확인됨.
3. 브라우저 동작(과목별 목록이 실제로 뜨는지, 클릭 시 문구가 뜨는지)은 사용자가 직접 확인해야 한다. 아래 "직접 확인하실 것" 참고.

### 참고 / 남은 일

- 지금은 형식이 잘못된 덱을 넣어도 "읽지 못했습니다" 정도로만 뜬다. "문제 id + 구체적 이유"까지 보여주는 것은 3단계에서 `validator.js`가 맡는다.
- 아직 클릭해도 실제로 문제를 풀 수는 없다(4단계 이후).

### 다음 단계 예고

## 3단계: 형식 검사기

- **날짜**: 2026-09-25
- **상태**: 완료 (사용자 확인 대기)

### 목표

일부러 망가뜨린 덱 파일을 넣어도 앱이 멈추지 않고, 어디가 잘못됐는지(파일명 + 문제 id + 이유) 홈 화면에 표시되게 한다.
오류가 있는 문제만 제외하고 나머지는 계속 풀 수 있어야 한다(진짜로 풀 수 있는지는 4단계 이후에 확인 가능).

### 진행 과정 중 방향 확인

사용자가 "실제 문제를 만들어줄 필요는 없고, 그저 구동하는 시스템을 만들어주면 된다"고 재확인함(2단계에서 이미 확인된 방침 유지). 이번 단계도 검사 로직 자체(시스템)에 집중했다.

### 만든 파일 / 고친 파일

| 파일 | 변경 | 역할 |
|---|---|---|
| `js/validator.js` | 새로 만듦 | 헤더 필수 필드, deckId 중복, 문제 id 중복/누락, question·answer 빈 값, 객관식 choices/answer 일치, 주관식 answer 검사. DOM을 모르는 순수 함수로만 구성. |
| `js/main.js` | 고침 | loader 결과를 validator로 3단계(헤더 검사 → deckId 중복 검사 → 문제별 검사)로 걸러서 화면에 넘기는 `buildDeckEntries()` 추가. |
| `js/ui/home.js` | 고침 | 덱 전체 제외 사유와 문제별 오류를 "파일명 (+ id): 이유" 형태로 모아 보여주는 오류 박스 추가. 정상 덱은 오류 문제를 뺀 개수로 표시. |

### 내린 결정과 이유

- **`validator.js`는 DOM을 전혀 다루지 않는다**: CLAUDE.md 설계 원칙(관심사 분리)에 맞춰, 검사 로직은 데이터만 받고 데이터만 돌려주게 했다. 화면에 어떻게 보여줄지는 전적으로 `home.js`가 결정한다. 나중에 검사 규칙이 바뀌어도 화면 코드를 건드릴 필요가 없다.
- **검사를 3단계로 순서대로 진행**: (1) 헤더 필드 → (2) deckId 중복 → (3) 문제별 오류. deckId 중복 검사는 헤더가 정상인 덱들끼리만 비교해야 의미가 있어서(깨진 덱의 undefined deckId끼리 "중복"으로 잘못 묶이는 것을 방지) 순서를 이렇게 정했다.
- **문제 id가 없거나 정수가 아니면 그 문제 자체를 통째로 오류 처리**: 그런 문제는 전역 ID(`deckId/id`)를 만들 수 없어서 기록과 연결이 불가능하기 때문이다. 오류 목록에는 `id: "(id 없음)"`으로 표시한다.
- **오류가 있는 문제는 valid 목록에서 제외하되, id 중복 검사용 `seenIds`에는 정상 처리된 첫 문제의 id만 넣는다**: 같은 id가 3번 나와도 첫 번째만 살고 나머지 둘 다 "중복" 오류로 잡히게 하기 위함.
- **오류 표시를 하나의 박스로 통합**: 덱 전체 제외(fatal)와 문제별 오류(questionErrors)를 같은 모양(`⚠️ 파일명: 이유` / `⚠️ 파일명 (id N): 이유`)으로 홈 화면 위쪽에 모아 보여줘서, 사용자가 한눈에 어디를 고쳐야 할지 보게 했다.
- **정상 덱 카운트 표시 방식**: 오류 문제가 하나도 없으면 그냥 "N문제", 일부만 오류면 "M문제 (전체 N개 중 형식 오류 K개 제외)"로 표시해 헷갈리지 않게 했다.

### 확인 방법과 결과

## 4단계: 퀴즈 엔진 + 객관식

- **날짜**: 2026-09-25
- **상태**: 완료 (사용자 확인 대기)

### 목표

덱을 클릭하면 객관식 문제가 순서 섞여 나오고, 답하면 즉시 채점되며, 끝까지 풀면 "N문제 중 M개 정답" 결과가 나오게 한다.
이 단계에서 주관식 문제는 건너뛴다(렌더러가 아직 없으므로 자동 제외).

### 만든 파일 / 고친 파일

### 내린 결정과 이유

- **렌더러 자체 등록 방식(`registerRenderer`)**: `mcq.js`는 로드되는 순간 스스로 `registry.js`에 등록한다. 그래서 5단계에서 `short.js`를 추가할 때도 `engine.js`나 `quiz.js`를 고칠 필요 없이, "렌더러 파일 추가 + `main.js`에 import 한 줄" 만으로 새 유형이 붙는다. 설계 원칙 3(엔진은 유형을 모름, 새 유형 추가 = 렌더러 파일 + 등록 한 줄)을 그대로 구현한 것이다.
- **`detectType`은 CLAUDE.md의 "유형 판단 규칙"을 그대로 옮김**: `type` 필드가 있으면 그 값을 쓰고, 없으면 `choices` 유무로 판단한다. 지금은 어떤 덱도 `type` 필드를 안 쓰지만, 나중에 새 유형이 추가돼도 기존 덱 파일을 고치지 않아도 되도록 이 규칙을 문서 그대로 지금 넣어 뒀다(새 기능을 미리 만든 것이 아니라 문서에 이미 확정된 규칙을 옮긴 것).
- **주관식은 "렌더러 없음 → 자동 제외"로 건너뜀**: `quiz.js`가 `validQuestions`를 `hasRenderer(detectType(q))`로 걸러서 재생 목록을 만든다. `engine.js`에 "주관식은 건너뛴다"는 로직을 넣지 않았다 — 그 특수 처리를 알면 나중에 필요 없어질 임시 지식이 엔진에 남기 때문이다. 5단계에서 `short.js`를 등록하면 이 필터를 거치지 않고 자동으로 같이 섞여 나온다(엔진·quiz.js 코드 수정 없음).
- **문제 전역 ID는 엔진이 붙인다**: `createQuizSession`이 `source`(=deckId)와 문제의 `id`로 `qid = "${source}/${id}"`를 만들어 렌더러와 결과에 넘긴다. 렌더러 규칙(문서)에서 "question: 문제 객체(전역 ID 포함)"라고 했으므로, 전역 ID를 붙이는 책임은 엔진에 두고 렌더러는 그냥 받아서 쓰기만 하게 했다.
- **숫자키 리스너는 답을 확정하면 바로 해제**: `mcq.js`가 `document`에 `keydown` 리스너를 붙이는데, 채점 직후 `removeEventListener`로 정리한다. 안 그러면 문제를 넘길 때마다 이전 리스너가 계속 쌓여서(메모리 누수) 나중에 문제가 많은 덱에서 느려질 수 있었다.
- **Enter로 다음 문제는 `quiz.js`(UI)가 담당, 렌더러는 모름**: CLAUDE.md 규칙 "다음 버튼과 화면 전환은 엔진/UI가 담당한다"에 따라, `quiz.js`가 `document`에 Enter 키 리스너를 하나만 두고 "다음" 버튼이 보일 때만 반응하게 했다. `mcq.js`는 숫자키로 "선택"만 처리하고 "다음"은 전혀 모른다 — 이렇게 해야 5단계에서 `short.js`(Enter로 제출/다음)를 추가해도 이 Enter 처리 흐름을 그대로 재사용할 수 있다.
- **`renderQuiz`가 재생할 문제가 0개면 안내 후 홈으로**: 어떤 덱이 전부 주관식이라 이번 단계에서 풀 수 있는 문제가 하나도 없을 수 있다. 이 경우 빈 결과 화면으로 바로 넘어가는 대신 "지금은 풀 수 있는 문제가 없습니다"라는 안내와 홈으로 가기 버튼을 보여줘 사용자가 당황하지 않게 했다.
- **home.js의 "선택한 덱" 문구를 없애고 클릭하면 바로 퀴즈 시작으로 바꿈**: 2단계 완료 기준이던 문구 표시는 이제 실제 풀이 화면으로 대체되는 것이 자연스러워서 정리했다(개인용 앱이라 중간 확인 단계를 넣지 않음).

### 확인 방법과 결과

이번에도 이 환경에는 node/브라우저가 없어 자동 실행 테스트는 못 했다. 대신:
1. 새 파일들의 문법과 로직을 손으로 검토했다.
2. `python3 -m http.server` + `curl`로 모든 새 파일(`engine.js`, `ui/quiz.js`, `ui/result.js`, `renderers/registry.js`, `renderers/mcq.js` 등)이 200으로 정상 응답하는지 확인했다.
3. **실제 풀이 동작(선지 섞임, 채점 색상, 숫자키/Enter, 결과 화면)은 사용자가 브라우저에서 직접 확인해야 한다.**

### 참고 / 남은 일

- 주관식 문제가 섞인 덱을 풀면, 이번 단계에서는 주관식 문제 수만큼 문제 수가 줄어서 나온다. 정상 동작이며 5단계에서 해결된다.

## 5단계: 주관식

- **날짜**: 2026-09-25
- **상태**: 완료 (사용자 확인 대기)

### 목표

객관식·주관식이 섞인 덱을 끝까지 풀 수 있게 한다. 주관식은 정규화 비교로 채점하고, 오답이면 "맞은 걸로 처리" 버튼으로 정정할 수 있어야 한다. `engine.js`는 전혀 수정하지 않는다.

### 만든 파일 / 고친 파일

| 파일 | 변경 | 역할 |
|---|---|---|
| `js/renderers/short.js` | 새로 만듦 | 주관식 렌더러. 입력창+제출(Enter로 제출), 정규화 후 비교, 복수 정답 지원, 오답 시 정답 표시 + "맞은 걸로 처리" 버튼. import되는 순간 `registerRenderer("short", render)` 호출. |
| `js/main.js` | 고침 | `renderers/short.js` import 한 줄 추가 (유형 등록). |
| `js/ui/quiz.js` | 고침 | 채점 결과를 즉시 `session.submitAnswer()`에 넘기지 않고 `pendingAnswer`에 잠시 보관했다가, "다음"으로 넘어갈 때(`goNext()`)만 엔진에 확정해서 넘기도록 변경. `engine.js`는 손대지 않음. |
| `css/style.css` | 고침 | 주관식 입력창, 제출 버튼, 정답/오답 표시, "맞은 걸로 처리" 버튼 스타일 추가. |

### 내린 결정과 이유

- **"맞은 걸로 처리"를 엔진 수정 없이 구현**: CLAUDE.md 5단계 조건이 "엔진 코드는 수정하지 않는다"이므로, 정정 로직을 `engine.js`가 아니라 `quiz.js`에 뒀다. 방법: 렌더러의 `onAnswer` 콜백이 호출되면 바로 `session.submitAnswer()`를 부르는 대신, 결과를 `pendingAnswer` 변수에 잠깐 담아 두고 "다음"으로 넘어갈 때만 엔진에 확정해서 넘긴다. `short.js`는 오답 판정 직후 "맞은 걸로 처리"를 누르면 `onAnswer({correct: true, ...})`를 **다시** 호출하는데, `quiz.js`는 이 두 번째 호출을 그냥 `pendingAnswer`를 덮어쓰는 것으로 처리한다. 결과적으로 엔진에는 항상 최종(정정된) 결과 한 번만 전달된다.
  - 부수 효과(좋은 점): 6단계에서 `storage.js`를 연결할 때도 "정답이 확정된 시점(다음으로 넘어갈 때)"에 기록하면 되므로, 정정 여부와 상관없이 항상 최종 값만 기록하면 된다. 추가 구조 변경이 필요 없다.
- **정규화 순서**: CLAUDE.md에 적힌 순서(앞뒤 공백 제거 → 중간 공백 제거 → 영문 소문자화 → NFC 정규화) 그대로 구현했다. 순서를 바꾸면 예를 들어 소문자화 이전에 NFC를 하는 것과 결과가 달라질 수 있는 자모 결합 문자가 있을 수 있어 문서 순서를 그대로 지켰다.
- **`isCorrect`는 `answer`가 배열이면 하나라도 일치하면 정답으로 처리**: CLAUDE.md 규칙 그대로. `Array.isArray`로 배열/문자열 모두 지원한다.
- **오답 시에만 정답과 "맞은 걸로 처리" 버튼 표시**: 정답을 맞혔을 때 굳이 정답을 또 보여줄 필요가 없어서, 오답일 때만 노출했다.
- **입력창은 채점 후 비활성화**: mcq.js가 답 확정 후 선택지를 잠그는 것과 같은 방식으로, 중복 제출을 막았다.
- **Enter 키 흐름 재확인**: 문제를 풀 때 Enter를 누르면 `<form>`의 기본 제출 동작으로 채점된다. 채점 후 다시 Enter를 누르면(이번엔 입력창이 비활성화라 폼이 아니라 `quiz.js`의 전역 Enter 리스너가 반응) "다음"으로 넘어간다. 같은 Enter 입력 한 번으로 "제출"과 "다음"이 동시에 발동하지 않는지: 제출 시점엔 아직 `nextBtn`이 숨겨져 있어 전역 리스너 조건(`!nextBtn.hidden`)을 통과하지 못하므로 안전하다.

### 확인 방법과 결과

이 환경에는 JS 실행 도구가 없어 이번에도 자동 실행 테스트는 하지 못했다. 코드를 손으로 검토하고, `curl`로 새/변경 파일이 200으로 서빙되는지 확인했다. **실제 채점 동작(정규화 비교, 복수 정답, 맞은 걸로 처리, Enter 흐름)은 사용자가 브라우저에서 직접 확인해야 한다.**

### 참고 / 남은 일

### 만든 파일 / 고친 파일

| 파일 | 변경 | 역할 |

### 내린 결정과 이유

- **`recordAnswer` 호출 위치는 `engine.js`**: 5단계에서 만든 `pendingAnswer` 지연 제출 구조 덕분에, `session.submitAnswer()`가 호출되는 시점은 이미 "맞은 걸로 처리"까지 반영된 최종 값이 확정된 뒤다. 그래서 `submitAnswer` 안에서 바로 `recordAnswer`를 불러도 정정된 값이 그대로 기록된다. CLAUDE.md의 엔진 스펙("답이 확정될 때마다 storage.js에 기록을 요청한다")과 정확히 일치하고, 4단계 때 미리 남겨둔 TODO 주석 자리를 그대로 채운 것이다.
- **`localStorage` 접근은 `storage.js` 안에서만**: `engine.js`, `main.js`, `ui/*.js`는 모두 `storage.js`가 내보낸 함수만 부르고, `localStorage.getItem`/`setItem`을 직접 건드리지 않는다. 설계 원칙 6을 그대로 지킨 것이며, 나중에 저장소를 온라인 DB로 바꿔도 `storage.js`만 고치면 된다.
- **저장 데이터 검증은 "최소 모양만" 확인**: `load()`가 JSON 파싱에 성공해도 `questionStats`/`sessions`/`answerLog`/`bookmarks`의 타입이 이상하면 기본 구조로 되돌아가게 했다. 깨진 localStorage 값 때문에 앱이 멈추는 일을 막기 위함이다(설계 문서의 "저장 데이터가 없거나 깨져 있으면 빈 기본 구조로 시작" 요구사항).
- **세션 저장은 `main.js`에서, 문제별 기록은 `engine.js`에서**: "세션"(덱 하나를 끝까지 푼 기록)은 화면 전환을 담당하는 `main.js`가 퀴즈 종료 시점을 알기 때문에 거기서 `saveSession()`을 부르는 게 자연스러웠다. 반면 "문제 하나 풀 때마다"의 기록은 그 시점을 정확히 아는 `engine.js`가 담당한다. 이렇게 나누니 어느 쪽도 상대방의 책임(언제 끝나는지 / 언제 한 문제가 확정되는지)을 넘겨받지 않는다.
- **`getDeckSummary`의 "최고 점수" 기준은 정답률(%) 우선, 동률이면 맞은 개수**: 덱마다 문제 수가 형식 오류로 인해 회차별로 달라질 수 있어서(예: 오류 문제가 나중에 고쳐짐) 맞은 개수보다 정답률을 기준으로 비교하는 게 더 공정하다고 판단했다.
- **결과 화면을 "틀린 문제만" → "전체 문제 + 정답률"로 교체**: 4단계의 "임시 결과 화면"은 문서에 "점수와 틀린 문제만"이라 명시돼 있었고, 6단계 목표는 "결과 화면에 문제별 누적 정답률"이므로 이번에 정식 형태로 교체했다. 정답/오답 모두 보여줘야 각 문제의 누적 정답률을 다 확인할 수 있어서 전체 목록으로 바꿨다.
- **"다시 풀기" / "틀린 문제만 다시 풀기" 버튼은 아직 안 만듦**: 최종 화면 구성 목표에는 있지만 6단계 완료 기준에는 없어서, 이번 단계 범위를 넘지 않기 위해 미뤘다.

- `git log`로 첫 커밋이 `main` 브랜치에 잘 만들어졌는지 확인.
- **내보내기/불러오기 버튼의 실제 동작(파일 다운로드, 불러온 뒤 점수 반영)은 사용자가 브라우저에서 직접 확인해야 한다.**

### 내린 결정과 이유

- **시약은 SMILES가 아니라 자유 글자로**: 라이브러리 기본 방식(`A>시약>B`)은 시약을 분자식으로만 보여줘서 "PCC", "1) BH₃ 2) H₂O₂", "가열" 같은 유기화학 표기를 못 쓴다. `|위|아래` 글자를 따로 받게 했고, 위 글자를 생략하면 라이브러리 기본 방식을 그대로 쓴다.
- **`|`를 구분 기호로 선택**: 반응 SMILES에서 쓰이지 않는 기호다.
- **해석 확인을 richtext.js로 모음**: 라이브러리를 아는 파일을 하나로 줄였다. 나중에 라이브러리를 바꿔도 이 파일만 고치면 된다.
- **반응식 크기**: 라이브러리가 style로 준 폭을 속성으로 옮기고, 높이는 viewBox 비율로 계산해 화살표 위·아래 글자가 잘리지 않게 했다. 좁은 화면에서는 CSS가 비율대로 줄인다.
- **전자 이동 화살표는 하지 않음**: SMILES로는 표현할 수 없다. 11단계 그림 파일 지원으로 해결한다.

### 확인 방법

- 유기화학 "2차시" 덱에서 6·7번 문제의 반응식(화살표, 위·아래 글자)이 보이는지 확인.
- `>>`를 지우는 등 반응식을 망가뜨리면 홈에 `반응식 해석 실패` 경고가 떠야 한다.
- 이 환경에는 브라우저가 없어 실제 표시는 사용자가 확인해야 한다.

## 11단계: 그림 파일

- **날짜**: 2026-09-30
- **상태**: 완료 (브라우저 확인은 사용자가 직접)

### 목표

SMILES로 표현할 수 없는 전자 이동(굽은) 화살표, 반응 메커니즘을 그림 파일로 넣을 수 있게 한다.

### 만든 파일 / 고친 파일

| 파일 | 변경 | 역할 |
|---|---|---|
| `js/ui/richtext.js` | 고침 | `[[img:경로|설명]]` → `<img src="decks/경로">`. 경로 규칙 검사, 못 읽으면 `[그림 없음: 경로]` |
| `js/validator.js` | 고침(주석) | 기존 `checkStructure`가 img 경로 규칙까지 검사하므로 코드 변경 없이 적용됨 |
| `css/style.css` | 고침 | 그림은 한 줄 차지, 화면보다 크면 비율대로 축소 |
| `decks/orgchem/images/sn2-mechanism.svg` | 새로 만듦 | 굽은 화살표 2개가 있는 SN2 메커니즘 예시 그림(직접 작성한 SVG) |
| `decks/orgchem/02-structures.json` | 고침 | 8번 문제(메커니즘 그림) 추가 |
| `docs/PROMPT.md`, `CLAUDE.md` | 고침 | 사용법, 자주 생기는 실수 |

### 내린 결정과 이유

- **경로는 `decks/` 기준**: `index.json`과 같은 규칙이라 헷갈리지 않고, 덱과 그림을 같은 과목 폴더에서 관리할 수 있다.
- **인터넷 주소·`..` 금지**: 외부 그림은 사라질 수 있고, 앱 폴더 밖 파일은 GitHub Pages에 올라가지 않는다.
- **파일 존재 여부는 검사기가 아니라 그릴 때 확인**: 검사기는 동기(즉시) 검사라 파일을 받아볼 수 없다. 대신 그릴 때 실패하면 그 자리에 경고를 보여준다. 홈에서 미리 알려주는 것은 12단계 점검 때 다시 검토한다.
- **AI는 그림을 만들지 않음**: 좌표가 필요한 그림은 AI가 정확히 만들기 어렵다. 그림은 사용자가 도구로 그리고, 덱에는 경로만 적는다.

### 확인 방법

- 유기화학 "2차시" 8번 문제에 SN2 메커니즘 그림(빨간 굽은 화살표 2개)이 보여야 한다.
- 경로를 없는 파일로 바꾸면 `[그림 없음: ...]`, `http://`로 바꾸면 홈에 경로 경고가 떠야 한다.

### 확인 방법과 결과

- 로컬 서버에서 HEAD 요청이 있는 그림은 200, 없는 그림은 404로 응답하는 것을 확인했다.
- 사용자 요청으로 점검표를 Claude가 직접 수행했다. 방법: 앱 폴더 밖(임시 공간)에 Python용 Playwright와 화면 없는 Chromium을 설치하고(sudo 불필요), 점검표 24개 + 기준 확인 3개를 자동으로 "망가뜨리기 → 새로고침 → 경고 읽기 → 되돌리기" 하는 스크립트를 돌렸다. 앱 코드에는 테스트 도구가 들어가지 않는다.

## 추가 작업: 홈을 과목별 페이지로 나누기 (2026-10-10)

덱이 많아져(69개) 홈 한 페이지가 너무 길어졌다. 사용자에게 "과목 선택 화면 → 과목 페이지" 방식과 "위쪽 탭" 방식을 제시했고, 과목 선택 화면 방식으로 결정했다.

- `js/ui/home.js`: `renderHome(container, entries, subject, callbacks)`로 바꿨다. `subject`가 없으면 과목 목록(덱 수·문제 수)과 백업 버튼·형식 오류 경고를, 있으면 "← 과목 목록" 버튼과 그 과목의 덱 목록을 그린다. 존재하지 않는 과목명이면 과목 목록으로 돌아간다.
- `js/main.js`: 현재 과목을 주소의 `#과목명`으로 관리한다. 과목 클릭은 주소만 바꾸고, `hashchange` 이벤트에서 화면을 다시 그린다. 그래서 브라우저 뒤로가기가 동작하고 과목 페이지를 즐겨찾기할 수 있다. 퀴즈 후 "홈으로"를 누르면 주소가 그대로이므로 보던 과목 페이지로 돌아간다.
- `css/style.css`: 쓰지 않게 된 `.subject-group`을 지우고 `.back-button`을 추가했다.
- 덱 파일 형식, 기록 저장 구조는 바꾸지 않았다.

확인 방법: 홈에 과목 목록만 보임 → 과목 클릭 시 주소가 `#과목명`으로 바뀌고 그 과목 덱만 보임 → "← 과목 목록" 또는 브라우저 뒤로가기로 복귀 → 덱을 풀고 "홈으로"를 누르면 같은 과목 페이지로 돌아옴.
